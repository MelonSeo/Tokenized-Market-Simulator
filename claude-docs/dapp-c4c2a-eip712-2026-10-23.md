# C4c-2a — C EIP-712 digest와 EOA 서명 검증 단위

작성: 2026-10-23. **구현 완료, 실제 Java 실행·독립 검토 결과는 총괄 진행 문서에서 연결한다.** Receipt/canonical proof·실환경 인수를 완료했다는 의미가 아니다.

## 1. 변경 범위와 API

신규 `custody/proof/CEip712Verifier.java`, `CEip712VerifierTest.java` 및 이 문서만 작성했다. 기존 reviewed call ABI의 immutable `CAbiModels.Intent/Report`를 입력으로 재사용하며 기존 ABI·reducer·store·runner·계약·보호 worktree는 수정하지 않았다.

- `intentTypeHash/intentStructHash/intentDomain/intentDigest`
- `reportTypeHash/reportStructHash/reportDomain/reportDigest`
- `recover(digest,signature)`
- `verifyIntent(...,expectedOwner,signature)` / `verifyReport(...,expectedOracle,signature)`

정확히 C Intent 22개 필드와 Report 18개 필드를 Solidity 순서·32바이트 word로 hash한다. C user domain은 `TokenizedMarketCFuturesUserIntent/1/controller`, Report domain은 `TokenizedMarketFutures/1/rules`다. 같은 chainId라도 서로 다른 verifyingContract/name/struct type/policy가 기존 B 서명과의 분리를 만든다. chainId는 nonzero uint256, verifyingContract 및 expected signer 주소는 nonzero다.

EOA는 65-byte ECDSA만 지원한다. r은 `0<r<n`, s는 `0<s<=n/2`, v는 27/28을 강제한다. high-s를 정규화하여 수락하거나 v0/1을 자동 변환하지 않는다. EIP-2098 compact/1271 fallback은 없다. expectedOwner는 Intent.owner와 일치해야 하며 서명 복구 주소와도 대조한다. Oracle expectedSigner는 Report.executor와 혼동하지 않고 명시 입력으로 받는다. 오류는 고정 `C_EIP712_*` 코드만 반환하며 원본 서명·digest·예외 cause를 출력하지 않는다.

반환 scope는 `DIGEST_AND_EOA_SIGNATURE_ONLY_NOT_TRANSACTION_OR_CANONICAL_PROOF`다. 서명이 맞아도 tx.from/to, calldata, JWT 귀속, 최신 nonce/version, 120/30초, 가격/수량 범위, Oracle 가격 진실성, risk/60초, Receipt/Event, canonical chain을 증명하지 않는다. 유효하지 않은 시간 window라도 cryptographic 서명이 맞을 수 있음을 테스트한다. 전체 권한·금융 검증은 후속 proof verifier에서 결합한다.

## 2. 독립 기준값

기존 `deployment/c-intent-golden.py`는 제품 Java·Solidity encoder/TYPE_HASH를 가져오지 않고 공개 숫자를 수동 32-byte word로 연결하여 로컬 `cast keccak`을 실행한다. 그 고정 C Intent 기준값을 재사용한다. 문서 작성 과정에서 실제 원본 스크립트와 값·타입 문자열을 읽었다.

```text
Intent word values = [int(0x11*20), int(0x22*20),3,4,5,6,0,0,0,1,10,0,0,
 100*10^18,99*10^8,101*10^8,9*10^18,11*10^18,7,1000,1120,8]
domain chainId=31337, verifyingContract=0x33*20
typeHash   ae1bef5d472f4b46787dd0444f164ec31ebf4fc901b01ddf69c8ddf6a1733ff7
structHash 08379fb7f965c1760c22f2c0ce8cec533b216d3fb5622bfc38f71c686e68b10f
domainHash a81cf76c7e65e2d4a39e6d9637dcf2f104fb9d94d819bdddfab0f733f3bc2c5a
digest     b81cb4bf2b9bad10a2613da0ec1df89549be8aaf991f3cf4149ef39ca02a3e67
```

신규 Report 기준값은 실제 `FuturesReportTypes.sol`의 전체 type literal을 읽고 **Java 제품 encoder 없이** PowerShell에서 수동 18 words를 연결한 후 local cast 1.5.1-stable `keccak`으로 산출했다. RPC/키/네트워크를 사용하지 않았다.

```text
Report words = [1,2,3,4,4,5,6,1,10,9,10,11,12,13,14,44,17,18]
// hash/address 자리도 같은 숫자를 uint word로 left-pad한 값이다.
domain name=TokenizedMarketFutures,version=1,chainId=31337,verifyingContract=0x44*20
typeHash   11abeea8e2bb530223ac3eff4001f9e95407652ac92788ceffc5c808ead6e6c6
structHash 347554e5d6c6e43609b2d5d1e9e357e68fe0471638fac42929926046c5f25434
domainHash 65543a891ab621ab903839b38ef11462507bd2d2bd7b0809c6aea919d3fe62f2
digest     9f4e33687a94c533d176a054aaf5d435999bd713e385eb52b5b064daf7fb9a30
```

재현 알고리즘은 `cast keccak(typeLiteral)`, `cast keccak(typeHash || 18*uint256word)`, `cast keccak(domainTypeHash || keccak(name) || keccak("1") || chainWord || addressWord)`, `cast keccak(0x1901 || domainHash || structHash)`다. 실제 hash 입력은 연결한 raw bytes를 `0x` hex로 전달한다. 이는 typed data encoding 기준이며 유효한 경제 거래나 실행 승인이 아니다.

## 3. 의존성과 테스트 범위

현재 cached classpath에서 다음을 읽기 전용 재사용한다. 다운로드·설치·의존성 변경을 하지 않았다.

- `org.web3j:crypto:4.12.2`
- `org.web3j:utils:4.12.2`
- `org.web3j:rlp:4.12.2`
- `org.bouncycastle:bcprov-jdk18on:1.78.1`

제품은 Hash.sha3와 Sign.signedMessageHashToKey/Keys.getAddress만 사용하며 Spring/Jackson/provider/RPC를 로드할 필요가 없다. 단위 테스트 서명은 명시적으로 작은 공개 시험 정수 17/23으로 만든 ECKeyPair만 사용한다. 기존 사용자·MetaMask·보존 Anvil 키를 읽거나 원문 키/서명을 출력하지 않는다. 서명 복구 라이브러리 API를 로컬 javap 출력으로 확인했지만 sandbox file-access 오류로 프로세스 exit1이어서 그 명령 자체를 실행 검증 PASS로 기록하지 않는다.

테스트는 고정 두 golden의 모든 단계, 정상 owner/Oracle, 22/18개 필드 각각 변조, chain/address/name/version/B domain, user/price domain 분리, r/s 범위·high-s malleation·v0/1 등 비표준 v, 64/66-byte/잘못된 hex/compact 거부, digest 길이, zero/malformed domain, expected owner/signer 대조, 개인 메시지 prefix 거부, uint256/uint8 최대 정밀도, 고정 실패 코드 및 cryptography-only 한계를 포함한다.

이 단위는 C4b PG 결과에 의존하지 않는 순수 암호 검증이다. 독립 Java 실행과 검토가 끝나기 전 완료 안전성을 선언하지 않는다. 후속은 C4c-2b의 실제 signed tx envelope/sender/hash 검증과, 그 뒤 C4c-2c의 direct/relay caller·전체 경제/시간 조건·Receipt 연결로 분리한다.

## 4. 총괄 직접 실행

`python deployment/c-proof-check.py`: Java21 compile/test exit0, **22PASS/0FAIL/0SKIP/0ABORTED**, source 불변을 확인했다. 신규 실행 `deployment/runtime/c-proof/20261023T014717Z-cb0c60f5`, scope `PURE_C_EIP712_ONLY`, sourceHash `944dcf438a6551120fef9d296f442c43887349a371deaa23eab83f97083c0fe3`다. 정확한 C/Report Solidity와 golden 생성기, 사용 Java/launcher/runner, 의존 jar SHA와 stdout/stderr를 보존했다.

캐시 crypto/utils/rlp/BouncyCastle4개와 JUnit7개만 로드하며 환경에서 API/DB/RPC 설정을 전달하지 않는다. 사용자 서명 요청이나 실제 네트워크 호출은0회다. 현재 최초 독립 검토 중이며 그 전에는 전체 거래 검증 완료로 승격하지 않는다. 저수준 digest/recovery 성공을 nonce·기한·Receipt·실제 caller 검증과 혼동하지 않는다.

최초 독립 검토에서 **발견된 필수 수정 없음**이다. 검토자는 실제22/18필드 Solidity와 Java, crypto API·독립 golden·변조/도메인/서명 경계22개, runner 및 원본22PASS/source 차이0을 확인했다. 검토자의 재실행은 없다. EOA code 상태·실제 tx caller·nonce·시간·금융·Receipt·canonicality는 여전히 별도 미구현 경계다.

다음 독립 C4c-2b에서 실제 signed transaction의 sender/hash/chain binding을 검증한다. 그 단위의 고정 selector를 shared runner에 추가했으므로 변경 runner는 C4c-2b 검토 범위에 포함하고 기존22개도 재실행한다. 이로써 과거22PASS의 sourceHash가 새 runner를 자동 검증했다고 주장하지 않는다.
