# C안 구현 전 사용자 정책 결정 — 5개 질문

> 2026-10-23 / 설계 검토용. **아래 추천은 승인된 정책이 아니다.** 토큰 발행·이동·DB/체인 변경·배포·유료 실행은 하지 않았다. 상세 근거와 필수 테스트는 [C안 설계 §12~21](dapp-c-custody-policy-design.md#12-2026-10-23-소스-재확인과-설계-경계)에 있다.

## 지금과 달라지는 점

현재 B-v2는 독립 지갑의 거래 동의를 컨트랙트가 검증하지만 담보는 DB 모의 장부다. C는 사용자 지갑에 실제 모의 ERC20을 주고 MarginVault가 예치·잠금·손익 귀속·인출을 강제하는 단계다. 이 모의 토큰은 실제 원화·주식 상환권이 아니다. 최신 B-v2 감사 Gate PASS는 C 자산 보관의 검증 결과가 아니며, C 구현·실자산 인수는 **NOT_RUN**이다.

## 특히 C-D03에서 오해하면 안 되는 것

유한 pool은 모든 미래 이익을 보장하지 않는다. 현재 산식에서 **Short 이익은 가격 0 방향에서 제한**되며 가격 상승 시 커지는 것은 Short 손실이다. Long 이익은 가격 상승에 따라 커지고, 소스의 기술 입력 상한이 pool 지급능력을 보장하지는 않는다. 어느 방향도 여러 포지션 합산 수익이 pool을 넘지 않는다고 가정할 수 없다.

사용자 손실은 담보 한도로 제한한다는 기존 산식을 유지하는 후보다. 담보 100/계산손실 130이라면 실제 잃는 자산은 100이고 badDebt 30은 별도 손실 기록이다. 이를 사용자 추가 청구액·pool 현금·새 토큰으로 취급하지 않는다. Claims를 선택하면 미지급 수익은 현금과 분리한 부채이며 인출 가능 잔고가 아니다.

현재 2/5/10배·담보 증액만·MM 5%에서는 양의 PnL 포지션이 위험 조건을 만족하지 않는다는 floor/ceil 불변식을 상세 문서에서 설명한다. 따라서 pool 부족은 이익 CLOSE의 가용성 문제로 정확히 구분한다. 청산은 Oracle/Report 부재나 향후 토큰 전송 실패 등 별도 원인으로 여전히 중단될 수 있다. 수학 보조 실험 PASS는 C 구현 인수가 아니다.

## 함께 확정해야 할 숫자·범위

- 총공급 **S**, 사용자 분배 **U**, pool 출자 **H**, 미배분 **R** (`S=U+H+R`)와 실제 출처/수령 방식. 예시 `H=10,000,000` 토큰은 기존 DB 초기값 비교일 뿐 승인·최종 추천 금액이 아니다.
- Faucet을 고르면 총예산·회당/주소한도·기간. Claims를 고르면 지급순서·부분지급·청구와 재충전 규칙. 출자자 인출을 허용하면 노출 중 회수 제한 규칙.
- Oracle 없는 비상정산까지 원하면 가격 근거·대기시간·손실 분담. 원하지 않으면 locked fail-closed의 한계를 명시한다.
- Oracle 교체권/지연, pause가 막을 OPEN/TOP_UP/CLOSE/청산/입금/출금의 정확한 표, owner/relayer/keeper Gas 부담. 수익 상한·포지션 노출 제한·최악 지급 예약은 자동 도입하지 않는다.

## 승인 후 순서와 설명 가능한 보장

정책 확정 → 토큰/Vault Foundry → 승인·금융·실자산 원자성 및 고갈 시험 → DB projection/복구·감사 → 새 격리 PG/Anvil → 실제 MetaMask → 서버/Oracle 중단 분리 시험 순서다. 기존 B-v2 계약은 immutable이고 Vault hook이 없으므로 새 배포가 필요하며 기존 서명을 C 자산 처분에 재사용하지 않는다. 이번에는 문서만 작성했고 이 순서를 실행하지 않았다.

검증 후 주장할 수 있는 목표는 “일반 OPEN/TOP_UP/CLOSE에는 요청별 사용자 승인 또는 직접 owner 호출이 필요하고, free 자산은 owner만 계약 규칙으로 직접 인출한다”이다. 자동청산은 예외적으로 **사전 동의한 위험 정책·60초 유예·적격 Report 조건**에 따르며 매번 사용자 서명을 요구하지 않는다.

price signer가 악의적 가격에 유효 서명하고 허용 keeper가 전달하면 계약 조건을 만족하는 청산도 경제적 손실을 만들 수 있다. **직접 자산 탈취 차단과 악의적 Oracle에 대한 손실 방어는 다른 보장**이다. C-D05에서 signer 키 보유 주체·relayer와의 분리·교체 권한도 확정해야 한다. “언제나 출금”, “무조건 지급”, “Oracle 진실성”, “Anvil 운영자로부터 네트워크 독립”, “완전한 비수탁 시스템”을 자동 보장하지 않는다. 위 다섯 선택을 확정하기 전 C 자산 이동 코드는 시작하지 않는다.
